Porting a Ray-Traced Black Hole from GLSL to HLSL

把 591 行 GLSL 着色器移植到 Windows Terminal 的 HLSL 接口——语言差异、API 约束和测地线积分的故事。

起点：一个终端里的黑洞

ghostty-blackhole 是 s0xDk 为 Ghostty 终端写的自定义像素着色器。它在终端内部运行实时 Schwarzschild 测地线积分， 每个像素独立追踪光子在黑洞附近的弯曲路径。效果包括：

  • 黑洞阴影——冲击参数低于 b_crit = 3√3/2 r_s 的光子螺旋坠入视界
  • 引力透镜——终端文字在爱因斯坦环内弯曲、放大、镜像；远端平滑过渡到弱场偏折
  • 吸积盘——Shakura-Sunyaev 温度分布 + 相对论 Doppler 致亮 + 开普勒轨道条纹。星际穿越同款
  • 光子环——r = 1.5 r_s 光子球附近自然形成的明亮细环
  • 引力时间膨胀——内轨道的条纹图案随黑洞增长而冻结

原版纯 GLSL，只跑在 macOS/Linux 的 Ghostty 终端上。Windows Terminal 用的是 HLSL——微软的 DirectX 着色语言。两种语言虽然都写 C-like 的 fragment shader，但在细节上足够不同， 不能直接粘贴。

第一关：语言翻译

GLSL 和 HLSL 的语法有大量微小差异，逐一处理几乎等于重写。以下是实际遇到的关键区别：

类型声明

// GLSL — 赋值时隐式 const
const float HOLE_RADIUS = 0.02;

// HLSL — 全局常量用 static const，全局非常量用 static
static const float HOLE_RADIUS = 0.0200;
static float g_time = 0.0;   // 运行时可变

内置函数名

这是最繁琐的部分。相同的数学语义，不同的函数名： 

// 向量运算
fract(x)   → frac(x)
mix(a,b,t)  → lerp(a,b,t)
mod(x,y)    → fmod(x,y)
inversesqrt → rsqrt

输入/输出语义

// GLSL — layout location 声明
layout(location = 0) out vec4 fragColor;

// HLSL — 语义后缀（: SV_POSITION, : SV_Target 等）
float4 main(float4 pos : SV_POSITION, float2 uv : TEXCOORD) : SV_Target

这些差异虽然琐碎，但在 591 行的着色器里散布了上百处。用正则批量替换可以解决大部分， 但有些需要按上下文判断——比如 GLSL 的 mod 可能是 fmod 也可能是 %，取决于参数类型。

第二关：消失的 Uniforms

这是移植的核心难题。原版 GLSL 使用了 Ghostty 特有的 uniform 变量：

Ghostty Uniform 含义 Windows Terminal
iDate.w 墙钟时间（秒/小时） ❌ 无。用 Time（着色器启动起算）替代
iTimeCursorChange 光标最后移动时间 ❌ 无。空闲检测器不可用
iCursorColor 光标颜色（Token 模式用） ❌ 无。Token 模式已移除

Token 模式 完全不可用——Windows Terminal 的像素着色器没有访问光标颜色 uniform 的管道。这个模式用于追踪 Claude Code 上下文窗口占用率，因 API 限制只能留在 Ghostty 版本里。

番茄钟模式 则有变通方案：用 Time（着法器启动后的秒数）替代 iDate.w（真实墙钟）。代价是计时在每次切换着法器特效时重置，但功能等价—— 黑洞在工作阶段逐渐长大，休息阶段保持最小。

另一个缺失是空闲检测——Ghostty 原版通过 iTimeCursorChange 检测用户离开终端，自动切换状态。HLSL 版没有这个能力，番茄钟纯粹基于运行时间，不管 你是否在打字。

第三关：数值精度与性能

Schwarzschild 测地线积分是数值敏感的。每像素追踪光子的 4 阶 Runge-Kutta 积分器使用 Binet 形式的加速度公式： 

a = -(3/2) * h^2 * x / r^5

// h: 守恒角动量（每像素不同）
// x: 光子在屏幕平面上的投影坐标
// r: 光子到黑洞的 3D 距离

N_STEPS（默认 48，定义在文件顶部）是性能的主要调节旋钮。步数越多，光线追踪 越精确（尤其是靠近光子球的绕行轨道），但 GPU 负载随之增加。在集成显卡上，48 步可能 已经吃力；降到 32 步仍有可接受的视觉效果。

GLSL 和 HLSL 的 float 都是 32 位，但编译器的优化策略不同。 HLSL 在 DirectX 11 上下文中对 rsqrt 的实现可能与 GLSL 的 inversesqrt 有微小差异，在 r^5 这样的高阶项上累积误差。 实测中，在冲击参数接近 b_crit 的边缘情况（光子几乎被捕获）， 两种实现的判别可能相差 1 个步长——这决定了该像素是阴影还是透镜。调整 N_STEPS 和积分收敛阈值可以弥补。

吸积盘：从 GLSL 到 HLSL 的逐行比对

吸积盘是着色器最复杂的子系统。它基于 Shakura-Sunyaev 薄盘模型的温度分布， 加上相对论 Doppler 致亮和开普勒速度场： 

// 黑体辐射 → RGB 近似（连续光谱积分）
vec3 blackbody(float T) {
    // 不使用查找表，直接多项式拟合 Planck 曲线
    ...
}

// 相对论 Doppler 因子
float g = sqrt(1.0 - 1.5 * r_s / r) / (1.0 - dot(beta, k_hat));

// 观测亮度 ∝ g^N_beaming
float beaming = pow(g, DISK_BEAM);

这一块完全是对 GLSL 原版的逐行翻译——数学完全一致，只是类型关键字和内置函数名不同。 测试时发现一个细节：GLSL 的 atan(y, x) 对应 HLSL 的 atan2(y, x)，不是 atan(x)。这种隐蔽差异在编译时不会报错， 但会让吸积盘的方位角偏移，导致条纹图案出现相位错误。只能通过对比原版渲染截图来发现。

交付

最终产物是两个独立的着色器文件：

  • blackhole.glsl — 原版 Ghostty 着色器（保留全部三种模式）
  • blackhole.hlsl — Windows Terminal 着色器（番茄钟 + 演示模式，Token 模式移除）

配一个 claude-token.py 辅助脚本（仅 Ghostty Token 模式用）， 以及 macOS 上可用的 SwiftUI 调参应用（tuner/），用于直观调整 20+ 个可调常量。

Windows Terminal 用户只需在 settings.json 中指定 experimental.pixelShaderPath，然后按 Ctrl+Shift+P → "切换终端视觉特效"。按作者的话说——"你的终端内容 就是被引力透镜弯曲的背景天空"。

整个移植过程让我对 GPU 着色器的跨平台性有了更深的理解：语言的差异虽然琐碎， 但可以系统解决；API 能力的差异才是真正的约束边界。Token 模式因平台 API 不足 而无法复现——这是硬件/驱动的架构决策，不是代码能绕开的。
